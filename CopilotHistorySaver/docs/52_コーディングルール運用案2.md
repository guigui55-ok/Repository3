# C# コーディングルール

## 基本方針

- 可読性と保守性を優先し、処理の意図が追いやすいコードを実装する。
- 必要以上に細分化したり、過度に抽象化したりしない。
- 既存コードがある場合は、明確な問題がない限り、既存の構成・命名・記述形式に合わせる。

## クラスとメソッドの分割

- クラスとメソッドは、原則として1つの明確な責務を持つようにする。
- メソッドは数十行程度をひとつの目安とするが、行数だけを理由に機械的に分割しない。
- クラスについては行数を基準にせず、責務が複数に分かれていないかを基準に分割する。
- 処理の分割によって呼び出し階層が不必要に深くならないようにする。

## 処理の流れ

- 条件分岐やループのネストは、可能な範囲で浅くする。
- エラー条件や処理不要条件は、早期リターンを使用して先に処理する。
- 複数の処理段階がある場合は、処理順序を把握できる実行メソッドを用意する。
- 実行メソッドには主要な処理の流れを記載し、各処理の詳細は必要に応じて別メソッドへ分割する。
- ただし、処理を細かく分けすぎて、全体の流れが追いにくくならないようにする。

## 入力値と事前条件の確認

- 入力値、設定値、ファイルの存在など、処理に必要な前提条件は主処理の開始前に確認する。
- 複数の確認処理がある場合や、確認処理が複雑な場合は、専用の検証メソッドへ分離する。
- 単純な null チェックや引数チェックは、無理に別メソッドへ分離せず、対象メソッドの先頭に記載してもよい。
- 検証エラーが発生した場合は、原因を判断できるメッセージを出力する。

## コメント

- コメントは、処理の目的、実装理由、制約、注意点などを補足するために記載する。
- コードを読めば明らかな処理を、そのまま説明するコメントは記載しない。
- 複雑な条件分岐、外部仕様への依存、将来変更時の注意点には、必要に応じてコメントを記載する。
- コメント量を増やすことよりも、コードとコメントの内容が一致していることを優先する。

## 元の案から調整したポイント

特に次の2点は変更した方がよいです。

### 「数十行で1つのクラスや関数」

メソッドについては目安になりますが、クラスまで数十行に制限すると、クラスが細かく分かれすぎる可能性があります。

そのため、

* メソッド：数十行程度を目安
* クラス：行数ではなく責務で判断

と分けています。

### 「エラーチェックは別メソッド」

すべて別メソッドにすると、単純なチェックでも呼び出しが増え、逆に読みにくくなります。

そのため、

* 複雑・複数・再利用する検証 → 別メソッド
* 単純な引数チェック → メソッド先頭でもよい

という緩いルールにしています。

## agent・skill・promptのどれにするか

| 種類                  | 主な用途                        |  今回の適合度 |
| ------------------- | --------------------------- | ------: |
| Custom instructions | リポジトリや対象ファイルに常時適用するルール      |      最適 |
| Agent               | 実装担当、調査担当、レビュー担当などの役割・行動を定義 |     補助的 |
| Skill               | 特定作業の手順、知識、スクリプトなどを再利用      | 現時点では不要 |
| Prompt              | 「最小プログラムを作る」など、その都度実行する作業依頼 |     不向き |

GitHub公式でも、custom instructionsは継続的に適用する指示、prompt filesは必要なときに呼び出す個別タスク、skillsは専門的な反復作業を実行するためのまとまりとして区別されています。[Repository custom instructions](https://docs.github.com/copilot/customizing-copilot/adding-custom-instructions-for-github-copilot)、[Prompt files](https://docs.github.com/en/copilot/tutorials/customization-library/prompt-files)、[Agent skills](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills)

├─ agents/
