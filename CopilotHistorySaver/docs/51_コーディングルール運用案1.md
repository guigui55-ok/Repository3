# コーディングルール
- コメントは適時丁寧に記載する。
- コードの実装は、ある程度の粒度でクラスや関数をする。（基本的に数10行程度で1つのクラスや関数にする）
- １つの処理について、呼び出しやネストを深くしない。
- １つの処理で多くの呼び出しやネストが深くなる場合は、実行メソッドを用意して、処理全容がわかるように実装する。（ただし、１関数で長くなりすぎないことを優先する）
- 変数のエラーチェックなどは、実行前に別メソッドで行うこと。


Copilot:
要望は、選択中のコーディングルールを「緩めで使いやすい形」に整理し、加えて運用先を `agent / skill / prompt` のどれにするか提案することですね。まずは現在の記述をベースに、重複や曖昧さを減らした短い運用ルール案と、用途別の使い分け方をそのまま実務で使える形で提示します。

以下の形にすると、比較的ゆるく運用しやすいです。

**コーディングルール（緩め・初版）**
1. 可読性優先  
処理の意図が読み取りにくい箇所だけ、短いコメントを入れる。  
2. 関数・クラスの粒度  
1つの関数やクラスは「役割が1つ」に見える大きさにする。行数は目安として数十行まで。  
3. ネストの抑制  
if やループの入れ子は浅く保つ。早期 return や小分け関数で見通しを良くする。  
4. 処理全体の見える化  
処理が長くなる場合は、上位の実行メソッドで手順を並べ、詳細は下位メソッドに分ける。  
5. 事前チェックの分離  
入力値チェックや前提条件チェックは、実行処理の前に別メソッドで行う。  

**補足（ルールを固くしすぎないための運用）**
1. これは絶対規則ではなく目安  
可読性・保守性が上がるなら例外を許容する。  
2. 迷ったら「読む人が追いやすいか」で判断  
規則順守より、理解しやすさを優先する。  
3. PR レビュー観点は最小限  
責務分離、ネスト深さ、入力チェックの3点をまず確認する。  

---

agent / skill / prompt の使い分けは、次がおすすめです。

**結論**
1. コーディングルール本体は Agent に置くのが最適  
2. 定型作業手順は Skill  
3. 単発の依頼文テンプレは Prompt  

**理由**
1. Agent  
実装時に常時効かせたい方針（今回のルール）と相性が良い。  
2. Skill  
「調査手順」「レビュー手順」など、特定タスクを再利用するのに向く。  
3. Prompt  
一時的な依頼や試行錯誤には速いが、継続運用だとブレやすい。  

**このプロジェクト向けの実務案**
1. まず Prompt で1〜2週間試す（ルールの言い回しを調整）  
2. 安定したら Agent に昇格（正式ルール化）  
3. 調査・レビューの反復作業だけ Skill 化  

必要なら次に、あなた向けに
- Agent 用の短い正式文（そのまま貼れる版）
- Skill 化すべき作業の候補 3〜5 個  
まで具体化します。
