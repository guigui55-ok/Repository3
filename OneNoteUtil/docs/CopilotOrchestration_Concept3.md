# GitHub Copilot オーケストレーション構築 構想書

この文書は、Copilot を用いた作業オーケストレーションの方針を、実装と運用に使える粒度まで整理した構想書である。  
目的は、手動プロンプトから始めて、prompt / agent / skill を段階的に定義し、再利用可能な作業手順へ昇格させることにある。

## 1. 目的

本構想の目的は、案件ごとに発生する調査、方針整理、ドキュメント作成、レビュー観点整理、実装支援を、Copilot で高い割合まで自動化することである。

ここでいう「自動化」は、単に回答を得ることではなく、次の流れをできるだけ固定化することを指す。

1. 入力条件をそろえる
2. Copilot に調査・整理・下書きを行わせる
3. 生成物をレビュー観点とともに出力させる
4. 人が最終承認する

最終目標は全工程の自動化だが、当面の現実的な目標は 9 割程度の省力化とする。  
この 9 割とは、調査、方針案、初稿、チェック観点、差分整理の主作業を Copilot が担い、最終判断のみ人が行う状態を指す。

## 2. 対象範囲

本構想の対象は、次のフェーズと成果物である。

* 基本構想書の作成
* 要求仕様書の作成
* 設計書の作成
* 試験仕様書の作成
* 仕様手順書、マニュアル類の作成

対象は小規模から中規模のツール開発を主とし、案件ごとに共通化できる手順を優先する。  
一方で、個別案件固有の判断が大きい部分は prompt に残す。

## 3. 基本方針

本構想では、作業を次の 4 層で扱う。

1. prompt: その場限りの依頼を素早く処理する
2. agent: 会話を挟みながら進める定型作業を扱う
3. skill: 手順が固定された再利用可能な作業を扱う
4. chain: これらを連結して、上流から下流へ成果物を引き渡す

方針として重要なのは、最初から完成形を狙わないことである。  
まずは手動プロンプトを使って作業し、その中で繰り返し使う形を抽出し、再利用できるものから順に定義する。

## 4. 成功条件

本構想の成功条件は、次の 3 点で判定する。

* 同じ種類の作業を、同じ入力形式で再実行できる
* 出力物の構成と粒度がほぼ一定になる
* 人の作業は最終確認と例外処理に寄る

逆に、毎回プロンプトを書き直さないと成立しない状態、あるいは出力の形式が都度ばらつく状態は、まだ成功とはみなさない。

## 5. prompt / agent / skill の昇格方針

### 5.1 昇格の考え方

まずはユーザーが手動でプロンプトを作成し、同種作業の繰り返しや再利用可能性を確認する。  
そのうえで、Copilot 側でも有効なテンプレート化候補を提案できるようにする。

昇格の可否は、回数だけではなく次の観点で判断する。

* 再利用頻度: 同じ目的で複数回使うか
* 入力の安定性: 毎回ほぼ同じ前提で使えるか
* 出力の安定性: 期待する成果物の形式が安定しているか
* 手順の固定度: 実行手順を明文化しやすいか
* 独立性: 単独の役割として切り出せるか
* 修正容易性: 失敗時に原因を追いやすいか
* チェイン適性: 前後工程と接続しやすいか

### 5.2 判定基準

* prompt に留める
	* 1 回限りの依頼
	* 内容が流動的
	* 会話のたびに大きく書き換える

* agent に昇格する
	* 同種作業が複数回ある
	* 会話の流れは必要だが、手順と出力をかなり固定できる
	* 中間成果物を段階的に作る作業に向く

* skill に昇格する
	* 手順がほぼ固定である
	* 判断基準を明文化できる
	* 複数案件で再利用できる
	* 入力条件がそろえば、ほぼ同じ流れで実行できる

### 5.3 昇格の実務ルール

昇格の目安として、次を採用する。

* 同じ目的の入力が 3 回以上発生したら、テンプレート化候補として記録する
* 出力の構成が 2 回以上安定したら、agent 候補として検討する
* 手順が 3 回以上ほぼ同一で、判断基準まで固定できるなら skill 候補とする

ただし、回数はあくまで補助指標であり、作業の安定性を優先する。

## 6. 成果物の型

各段階の成果物は、単なる自由文ではなく、次に渡せる形式でそろえる。

### 6.1 prompt の成果物

prompt は、その場で使える依頼文とする。

* 入力: 依頼内容、対象、制約、参照資料
* 出力: 下書き、整理結果、確認観点、差分案
* 用途: 1 回の作業に直接使う

### 6.2 agent の成果物

agent は、会話を挟みながら段階的に作る成果物とする。

* 入力: 定型化した依頼、必要な前提、途中確認の要否
* 出力: 中間案、整理済み案、次工程に渡せるドラフト
* 用途: 仕様整理、設計案、レビュー観点抽出、実装方針の詰め

### 6.3 skill の成果物

skill は、固定手順で再現可能な作業単位とする。

* 入力: 目的、前提、必要資料がそろった作業指示
* 出力: 固定フォーマットの成果物、チェック結果、実行記録
* 用途: 仕様書作成、レビュー支援、差分チェック、作業自動化

## 7. チェイン設計

本構想では、単独の prompt を増やすのではなく、連結可能な形を重視する。  
例えば、次の流れを想定する。

1. 依頼内容を prompt で整理する
2. その内容を agent で方針案にまとめる
3. 確定した手順を skill 化する
4. skill の出力を次の prompt または agent に渡す

チェインを成立させるため、各成果物は次の情報を明示する。

* 入力条件
* 出力形式
* 前工程の成果物名
* 次工程への引き渡し内容
* レビュー時の確認ポイント

## 8. 運用制約

### 8.1 クレジット消費

前回実装ではクレジット消費が大きかったため、今後は軽量な運用を優先する。

基本方針は次の通りとする。

* デフォルトの Plan エージェントは使わない
* 基本は Lite-Ask と Lite-Edit を使う
* 1 つの小規模プログラム作成につき、200 から 300 程度を目安とする
* 工程ごとに上限を決め、超過しそうなら一旦停止して見直す

### 8.2 ソース構成

実装で想定と異なる構成になったため、今後はソースファイル構成を先に決める。  
必要な場合は、次の情報を先に固定する。

* ディレクトリ構成
* ファイル名
* 成果物の保存先
* 生成順序
* レビュー対象範囲

### 8.3 レビュー

レビューは当面、人の目視を主とする。  
ただし、レビュー観点の抽出、差分要約、チェックリスト作成は Copilot に寄せる。

## 9. 進め方

1. 手動プロンプトで作業を回す
2. 反復される表現を prompt 化する
3. 会話ベースで定型化できるものを agent 化する
4. 手順と判断が固定されたものを skill 化する
5. それらを chain でつなぐ
6. 実運用の結果を見て、再び 1 に戻る

この循環を繰り返し、無理なく再利用率を高める。

* 実装プランからの実装
