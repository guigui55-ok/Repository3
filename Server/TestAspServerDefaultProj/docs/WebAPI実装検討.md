## 回答

はい、サーバー側とクライアント側に「同じ実装をコピーする」以外にも方法はあります。

### 1. 共通ライブラリを共有する
- `ResultInfo` / `ResultCode` を別プロジェクト（共通クラスライブラリ）に定義しておき、
- サーバー側とクライアント側の両方からそのライブラリを参照します。
- これならコードの重複がなく、定義は1つだけになります。

### 2. ASMX の参照生成に任せる
- `Add Web Reference` / `Service Reference` で生成されるプロキシには、
- サーバー側の `ResultInfo` / `ResultCode` に相当するクラス・列挙型が自動生成されます。
- この場合、クライアント側で手書き実装する必要はありません。

### 3. 単純な型に置き換える
- `ResultInfo` を使わず、`int` / `string` / `bool` といった基本型だけを返す方法もあります。
- 例えば `ResultCode` を `int` にして、`0=OK,1=Fail...` のように扱う。
- ただし可読性・拡張性は落ちます。

### 4. SOAP の標準エラー/フォルトを使う
- 成功・失敗の判定は `ResultCode` ではなく、SOAP Fault を使う構成もあります。
- ただしこれは今の `ResultInfo` の設計とは別方向です。

### 5. XML 形式・外部契約で統一する
- `ResultInfo` を XML シリアライズ可能な形にしておき、
- 同じ SOAP 名前空間／要素構造を両側で共有する。
- これも実質的には「共通契約」を持つ形です。

はい、ASMX の場合は「サーバーとクライアントで同じ契約を持つ」ことが一般的です。

### 具体的には
- サーバー側で `ResultInfo` / `ResultCode` を定義しておく
- クライアント側も同じ型の定義を使う、または
- `Add Web Reference` / `Service Reference` で生成されるプロキシを使って同等の型を使う

### その理由
- SOAP はメッセージ型の契約（WSDL / XML スキーマ）に基づくため
- サーバーとクライアントで型の解釈が一致していないと、デシリアライズで失敗したり
- `ResultCode` の値が違う意味で解釈されるリスクがあるため

### よくある方法
1. 共通ライブラリを参照する
2. プロキシ生成で同じデータ型を自動生成させる
3. もしくは、基本型（`int` + `string` など）にして契約をシンプルにする

> つまり「同じ実装を完全に手作業でコピーする」必要はないですが、両側で同じ契約・型定義を共有するのは一般的です。

GitHub Copilot: ## 「共通契約を明示的に共有する」概要

### 何をするか
- `ResultInfo` や `ResultCode` などのデータ型を、サーバー・クライアント双方で共通の形で定義する。
- 通常は、別の共通ライブラリ（Class Library）として切り出し、サーバー側プロジェクトとクライアント側プロジェクトの両方から参照する。

### 目的
- 同じ契約（同じ型定義）を両側で使うことで、型の解釈ズレを防ぐ。
- たとえば `ResultInfo.Result` の値が、サーバー側とクライアント側で意味が同じになる。

### 例
- `Common.Contracts.dll`
- `Common.Contracts` に `ResultInfo` と `ResultCode` を定義
- `TestAspServerDefault` と `TestAspClientDefault` がこの DLL を参照

### メリット
- 定義の重複を避けられる
- 変更が1箇所ですむ
- 型安全に開発できる

### 注意点
- ASMX では実行時に DLL を参照して通信するわけではなく、あくまでビルド時の型共有。
- SOAP の通信は WSDL/XML で行われるので、実際のメッセージ契約は XML スキーマに従う。

## 「生成プロキシで同じ型を再利用する」概要

### 何をするか
- Visual Studio の `Add Web Reference` / `Service Reference` で生成されるクライアント側プロキシに、
- 既存の共通型定義を使わせる設定を行う。

### もっと詳しく
- 通常、ASMX の参照追加では、サーバーの WSDL からクライアント用の型が自動生成される。
- そのとき、同名のクラスが既に参照アセンブリにあれば、
- `Reuse types in referenced assemblies` のような設定で、生成プロキシがその既存型を使える。

### 目的
- プロキシ生成による型の重複を避ける
- `ResultInfo` がクライアント側で2種類（プロキシ生成型と共通型）にならないようにする

### 例
- 共通ライブラリ `Common.Contracts.dll` を参照
- Web 参照追加時に「参照済みアセンブリの型を再利用」設定を有効
- 生成プロキシは `Common.Contracts.ResultInfo` を使い、別の新しい `ResultInfo` クラスは生成しない

### メリット
- クライアントコードがすっきりする
- キャストや互換性の問題が減る
- 共通型を正しく再利用できる

## 両者の関係

- 共通契約を明示的に共有する = 「契約そのものを共有する設計」
- 生成プロキシで同じ型を再利用する = 「生成されたクライアント側コードが、その共有契約を使う設定」

つまり、
1. まず `ResultInfo` / `ResultCode` を共通契約として定義し、
2. クライアント参照生成時にその契約を再利用する

という流れが理想です。
